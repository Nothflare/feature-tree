# Feature Tree v3.1.0 Design: Embedding Efficiency & Workflow-First Approach

**Date:** 2026-01-08
**Status:** Approved

---

## Overview

v3.1.0 focuses on two goals:
1. **Non-blocking embeddings** — `add_feature()`/`update_feature()` return immediately
2. **Workflow-first approach** — Claude starts with workflows, not code grep

---

## Part 1: Non-blocking Embeddings

### Problem

Current flow blocks while waiting for embedding API (up to 30s timeout):
```
add_feature() → embed_feature() → API call → ChromaDB write → return
                      ↑
              user waits here
```

### Solution

Fire-and-forget with visibility and retry.

```
add_feature()                          Background Worker
     │                                       │
     ├─► save to SQLite                      │
     ├─► queue embed job ──────────────────► │ (picks up job)
     ├─► return immediately                  │
     │                                       ├─► API call
     │                                       ├─► ChromaDB write
     │                                       └─► update embedding_status
```

### Implementation

**Background worker:**
- Single worker thread with `queue.Queue()`
- Processes one embed at a time
- Handles both features and workflows

**New column:** `embedding_status TEXT` on both `features` and `workflows` tables

```json
{"status": "success", "at": "2026-01-08T12:00:00Z"}
{"status": "failed", "error": "timeout", "at": "..."}
{"status": "pending"}
```

**Retry mechanism:**
- `update_feature(id="X")` with no other params = retry embedding
- `update_workflow(id="X")` with no other params = retry embedding

**Display in get_feature()/get_workflow():**
```
Embedding: ✓
Embedding: ✗ (failed 2h ago)
```

## Part 2: Workflow Schema Parity

### Problem

Workflows are missing v3 fields that features have.

### Solution

Add columns to `workflows` table:

| Column | Type | Purpose |
|--------|------|---------|
| `being_modified` | TEXT | none/building/refactoring/fixing/extending |
| `important_message` | TEXT | Claude-to-Claude sticky notes |
| `embedding_status` | TEXT | JSON status object |
| `archived_at` | TEXT | Soft delete timestamp |
| `steps` | TEXT | JSON array of human walkthrough steps |

**New `steps` field example:**
```json
[
  "Navigate to main interface",
  "Click the 'New Chat' button",
  "Verify a new conversation is created",
  "Check that chat area shows welcome state",
  "Verify conversation appears in sidebar"
]
```

## Part 3: Enhanced `get_workflow()` Output

### Problem

Current `get_workflow()` returns raw JSON blob. Not atomic documentation.

### Solution

Formatted output matching `get_feature()` style:

```
USER_ONBOARDING.signup [active] [building]
⚠️ Rate limiter needs 100ms delay

Description: Users create an account to start using the app
Purpose: Collects user data, triggers welcome email, initializes preferences

Steps:
  1. Navigate to signup page
  2. Enter email and submit
  3. Verify email via link
  4. Set password
  5. Complete profile form

Depends on (3):
  ✓ AUTH.register [active]
  ✓ AUTH.email_verify [active]
  ○ USER.profile_setup [planned]

Embedding: ✓
```

## Part 4: Field Definitions

Clear, well-defined purposes for all fields.

### Features

| Field | Audience | Content |
|-------|----------|---------|
| `description` | Human/YC partner | WHAT it does, user-facing behavior |
| `technical_notes` | Developer/Claude | HOW it works, implementation gotchas |

**Example:**
- `description`: "Allows users to log in with email and password"
- `technical_notes`: "Uses bcrypt, rate limited to 5 attempts/min, session stored in Redis"

### Workflows

| Field | Audience | Content |
|-------|----------|---------|
| `description` | Human/YC partner | WHAT the journey is, user-facing explanation |
| `purpose` | Developer/Claude | WHY it exists, technical/program-level goal |
| `steps` | Human walkthrough | The actual flow in plain language, like explaining to YC partner |

**Example:**
- `description`: "Users create an account and set up their profile to start using the app"
- `purpose`: "Collects required user data, triggers welcome email, initializes user preferences"
- `steps`: ["Navigate to signup", "Enter email", "Verify email", "Set password", "Complete profile"]

## Part 6: MCP Instructions & Docstrings

### Workflow-First Approach

The hierarchy for Claude:
```
Task arrives
    ↓
search_workflows("what user wants")  ← START HERE
    ↓
get_workflow(id) → atomic context for task
    ↓
get_feature(id) → zoom in for implementation detail
    ↓
Read code → finest detail (only specific files)
```

**Key insight:** One workflow often contains all context needed for a task. Don't grep the entire codebase.

### Updated Tool Docstrings

**`search_features`:**
> Semantic search finds conceptually related features (e.g., "auth" → login, signin, credentials).
> Use BEFORE exploring codebase, BEFORE creating features, BEFORE modifying code.
> Fast, free, prevents duplicates, produces context-aware results.

**`search_workflows`:**
> Semantic search for user journeys. Use FIRST — one workflow often contains all context needed for a task.
> Workflows → Features → Code.

**`get_feature`:**
> Use BEFORE modifying to see impact (used_by, linked_workflows).
> Use AFTER search to get full context.

**`get_workflow`:**
> Atomic documentation for a user journey.
> Use AFTER search_workflows to get full context including steps and feature dependencies.

### MCP Server Instructions Addition

```markdown
## Semantic Search

Feature Tree uses semantic search — finds conceptually related items, not just keywords.

"auth" → login, signin, credentials, session
"data storage" → database, cache, persistence

**Why this matters:**
- Fast, costs nothing, saves rework
- Context-aware results improve reasoning
- NEARLY 100% PREVENTS DUPLICATE FEATURES
- Dramatically increases reliability

## Workflow-First Approach

Workflows contain atomic context for tasks. Don't grep the entire codebase.

1. search_workflows → find relevant user journey
2. get_workflow → all context needed (steps, features, purpose)
3. get_feature → zoom in only when needed
4. Read code → only specific files, last resort
```

## Part 8: Migration

**New columns with defaults:**
```sql
ALTER TABLE workflows ADD COLUMN being_modified TEXT DEFAULT 'none';
ALTER TABLE workflows ADD COLUMN important_message TEXT;
ALTER TABLE workflows ADD COLUMN embedding_status TEXT;
ALTER TABLE workflows ADD COLUMN archived_at TEXT;
ALTER TABLE workflows ADD COLUMN steps TEXT;

ALTER TABLE features ADD COLUMN embedding_status TEXT;
```

**Existing features/workflows:** `embedding_status` starts as NULL (unknown). First update triggers re-embed.

## Implementation Order

1. **Schema changes** — Add columns to db.py with migration
2. **Background queue** — Worker thread + queue in embeddings.py
3. **Async embedding** — mcp_server.py queues instead of blocking
4. **get_workflow() upgrade** — Formatted output with steps
5. **Embedded text updates** — Add uses/steps to text functions
6. **Docstrings & instructions** — Update all tool descriptions
7. **Testing** — Verify non-blocking, retry, search quality
